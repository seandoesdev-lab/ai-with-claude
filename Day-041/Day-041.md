Phase 3 내내 우리는 "기호 8개", "기호 16개" 같은 장난감 어휘로 넘어갔습니다([[Day-037]]·[[Day-040]]). 실제 언어모델은 그 자리에 **학습된 토크나이저** 를 놓습니다. 오늘은 **BPE(Byte-Pair Encoding)를 의존성 없이 from scratch 로 학습** 시켜, 어휘가 만들어지는 과정을 merge 하나하나까지 들여다봅니다. 우리 코퍼스에서 BPE 가 가장 먼저 배운 규칙은 `공백+⟨eb⟩`(빈도 94)였고, 7번째로 바이트 쌍 `⟨8ba4⟩`, 15번째에 비로소 **글자 "다"** 가 완성됐습니다 — 한국어 한 글자가 어휘에 등재되기까지 merge 가 **두 번** 필요합니다. 이 사실 하나에서 오늘의 나머지가 따라 나옵니다: 같은 문장이 **어휘 300 에서 KO 70토큰·EN 61토큰, 어휘 880 에서 38·29토큰** 으로 줄고, 같은 어휘로 재도 한국어의 **글자당 토큰 비용이 영어의 2.76배** 이며, 학습 코퍼스를 영어 편중으로 바꾸면 **3.20배** 로 벌어지고 한국어 편중으로 바꾸면 **2.18배** 로 좁혀집니다. 마지막으로 `strawberry` 가 `st|ra|w|berry` 로 쪼개지는 것을 보고, "r 이 몇 개인가"라는 유명한 실패가 **모델의 지능이 아니라 입력 표현의 문제** 임을 확인합니다.

## 0. 들어가며 (Motivation)

[[Day-040]] 에서 Phase 3 을 닫으며 우리는 다섯 구조를 같은 과제에 세웠고, Transformer 가 여덟 거리 전부에서 `1.000` 을 냈습니다. 그런데 그 실험의 입력이 무엇이었는지 다시 보세요.

```text
  seq = [2, 9, 3, 11, 4, 13, 6, 10, 0, 12, 5, 15, 1, 14, 7, 8, 2]
```

**정수 열입니다.** 기호가 딱 16개였고, 그 16개는 우리가 손으로 정했습니다. 실제 언어모델도 입력은 똑같이 정수 열입니다 — 다른 점은 그 정수가 **텍스트에서 나온다** 는 것뿐입니다. 그 변환을 담당하는 것이 **토크나이저(tokenizer)** 이고, 오늘의 주제입니다.

[[Day-006]] 에서 이미 토큰화를 다뤘습니다. 하지만 그때는 **규칙 기반** 이었습니다 — 공백으로 자르고, 정규화하고, 불용어를 지웠습니다. 사람이 규칙을 썼습니다. Phase 3 을 지나온 지금 이 방식은 낯설게 느껴져야 합니다. [[Day-040]] §1.2 에서 정리한 Phase 3 의 한 문장이 이것이었기 때문입니다.

> **표현을 손으로 짜지 말고 데이터가 정하게 하라.**

토큰화도 예외가 아닙니다. **어휘도 학습됩니다.** 오늘 배울 BPE 는 "어떤 조각이 유용한가"를 코퍼스에게 물어보는 알고리즘입니다.

그리고 이건 사소한 전처리가 아닙니다. 토크나이저는 모델이 세상을 보는 **해상도** 를 정합니다. 여기서 정해진 것은 나중에 아무리 큰 모델로도 되돌릴 수 없습니다 — 문맥 창(context window)의 실질 길이, API 비용, 한국어 사용자가 겪는 불이익, 그리고 "`strawberry` 에 `r` 이 몇 개?"라는 질문 앞에서 최신 모델이 자꾸 틀리는 이유까지 전부 여기서 시작됩니다.

> Phase 3 taught us to *learn* representations instead of hand-crafting them. Tokenization is the last place where hand-written rules survived — and BPE is how we remove them. This is not preprocessing trivia: the tokenizer fixes the resolution at which a model perceives text, and no amount of scale undoes that choice.

## 1. 핵심 개념 (Core Concepts)

### 1.1 세 가지 선택지, 그리고 왜 둘은 실패하는가

텍스트를 정수 열로 바꾸려면 먼저 **무엇을 하나의 단위로 볼지** 정해야 합니다. 후보는 셋입니다.

| 단위 | 어휘 크기 | 시퀀스 길이 | 치명적 문제 |
|---|---|---|---|
| **단어(word)** | 수십만~수백만 | 짧다 | **미등록어(OOV)**. 오타·신조어·고유명사는 전부 `<UNK>` |
| **글자(character)** | 수십~수천 | **아주 길다** | 시퀀스가 4~5배 길어짐 → attention 비용 $O(T^2)$ 폭증 |
| **서브워드(subword)** | 3만~20만 | 중간 | — (그래서 이걸 씁니다) |

단어 단위의 문제는 특히 한국어에서 극심합니다. **교착어** 라서 "검색"·"검색은"·"검색을"·"검색에서"·"검색했다" 가 전부 다른 단어가 됩니다. 영어에서 어휘 5만이면 될 것이 한국어에서는 수백만이 필요하고, 그래도 처음 보는 활용형은 계속 나옵니다.

글자 단위는 OOV 가 없지만 대가가 큽니다. [[Day-040]] 에서 확인했듯 attention 은 $O(T^2)$ 입니다. 시퀀스가 4배 길어지면 계산은 **16배** 입니다.

**서브워드** 는 이 둘 사이의 타협입니다. 자주 나오는 것은 통째로(`the`, `검색`), 드문 것은 조각으로(`str`+`awb`+`erry`). 핵심 통찰은 이렇습니다.

> **빈도가 높은 것에 짧은 표현을 준다** — 이건 사실 데이터 압축의 원리입니다.

실제로 BPE 는 1994년 Philip Gage 가 만든 **압축 알고리즘** 이었고, 2016년 Sennrich 등이 기계번역의 OOV 문제를 풀려고 가져다 쓴 것입니다.

### 1.2 BPE 알고리즘 — 다섯 줄로 끝난다

놀랍도록 단순합니다.

```text
  1. 모든 텍스트를 최소 단위(바이트 또는 글자)로 쪼갠다.       -> 어휘 = 256
  2. 인접한 두 조각의 쌍 중 가장 자주 나오는 것을 찾는다.
  3. 그 쌍을 하나의 새 조각으로 합치고, 어휘에 등록한다.       -> 어휘 += 1
  4. 목표 어휘 크기에 도달할 때까지 2~3 을 반복한다.
  5. 합친 '순서' 를 저장한다. 이 순서가 곧 토크나이저다.
```

5번이 중요합니다. BPE 의 산출물은 단어 목록이 아니라 **순서가 있는 merge 규칙 목록** 입니다. 새 텍스트를 인코딩할 때는 **학습 때와 똑같은 순서로** 규칙을 적용합니다. 순서가 바뀌면 다른 분절이 나옵니다.

$$\text{어휘 크기} = (\text{기본 단위 수}) + (\text{merge 규칙 수})$$

바이트 단위라면 $256 + N$ 입니다. 그래서 "어휘 5만"은 "merge 규칙 약 49,744개"와 같은 말입니다.

### 1.3 byte-level BPE — OOV 를 원리적으로 없애기

GPT-2 가 도입한 변형입니다. 최소 단위를 **글자가 아니라 바이트** 로 잡습니다.

이유는 간단합니다. 유니코드 문자는 15만 개가 넘습니다. 글자 단위로 시작하면 기본 어휘가 이미 거대하거나, 아니면 못 본 글자에 `<UNK>` 를 써야 합니다. 반면 **바이트는 256개뿐이고, 세상의 모든 텍스트는 바이트로 표현됩니다.**

$$\text{어떤 문자열} \;\xrightarrow{\;\text{UTF-8}\;}\; \text{바이트 열} \;\Rightarrow\; \text{OOV 불가능}$$

이모지든, 처음 보는 한자든, 깨진 데이터든 전부 인코딩됩니다. 오늘 §4.4 에서 확인합니다.

**대가가 있습니다.** UTF-8 에서 ASCII 는 1바이트지만 **한글은 글자당 3바이트** 입니다.

| 문자 | UTF-8 바이트 | 개수 |
|---|---|---|
| `a` | `61` | 1 |
| `다` | `eb 8b a4` | **3** |
| `🍓` | `f0 9f 8d 93` | 4 |

즉 아무 merge 도 배우지 않은 상태에서 **한글 한 글자는 이미 3토큰** 입니다. 영어 알파벳은 1토큰이고요. BPE 가 merge 를 배우면서 이 격차를 줄여 나가는데, **그 merge 를 배우려면 코퍼스에 한국어가 충분히 있어야 합니다.** 오늘 §4.3 의 핵심이 이것입니다.

### 1.4 학습과 추론의 비대칭

BPE 에서 자주 혼동되는 지점입니다.

| | 학습(train) | 추론(encode) |
|---|---|---|
| 입력 | 큰 코퍼스 | 문장 하나 |
| 하는 일 | **어떤 쌍을 합칠지 결정** (빈도 기반) | **정해진 규칙을 순서대로 적용** |
| 빈도 사용 | 사용한다 | **사용하지 않는다** |
| 횟수 | 딱 한 번 (모델 학습 전) | 매 요청마다 |

추론은 빈도를 전혀 보지 않습니다. 규칙표를 순위대로 훑으며 "지금 적용 가능한 규칙 중 **가장 먼저 배운 것**"을 적용할 뿐입니다. 그래서 토크나이저는 **결정론적** 이고 아주 빠릅니다.

```python
# (발췌) bpe_from_scratch.py — 추론은 '가장 낮은 rank' 를 반복 적용할 뿐
while len(syms) > 1:
    best_rank, best_i = None, -1
    for i in range(len(syms) - 1):
        r = ranks.get((syms[i], syms[i + 1]))          # 먼저 배운 규칙일수록 rank 가 작다
        if r is not None and (best_rank is None or r < best_rank):
            best_rank, best_i = r, i
    if best_rank is None:
        break
    syms[best_i:best_i + 2] = [syms[best_i] + syms[best_i + 1]]
```

### 1.5 어휘 크기의 트레이드오프

"어휘를 키우면 토큰이 줄어드니 무조건 좋은 것 아닌가?" 아닙니다. 양쪽으로 비용이 붙습니다.

| 어휘 $V$ 를 키우면 | 좋아지는 것 | 나빠지는 것 |
|---|---|---|
| 시퀀스 길이 $T$ | **줄어든다** (attention $O(T^2)$ 이득) | — |
| 임베딩 행렬 | — | $V \times d$ **선형 증가** |
| 출력 소프트맥스 | — | 매 스텝 $V$ 개 로짓 계산 |
| 토큰당 학습 신호 | — | 희귀 토큰은 **거의 학습되지 않음** |

마지막 줄이 은근히 중요합니다. 어휘를 100만으로 키우면 대부분의 토큰은 학습 중 몇 번 보지도 못하고, 그 임베딩은 사실상 난수로 남습니다. 이런 **미학습 토큰(glitch token)** 은 실제로 모델을 이상하게 만듭니다.

그리고 오늘 실험에서 발견한 현실적 제약이 하나 더 있습니다. **어휘는 원한다고 커지지 않습니다.** 코퍼스에 "두 번 이상 인접해서 나오는 쌍"이 떨어지면 merge 가 멈춥니다. 우리 코퍼스로는 어휘 3000 을 요청해도 **880 에서 고갈** 됐습니다(§4.2). **큰 어휘는 큰 데이터를 전제합니다.**

### 1.6 토크나이저가 남기는 흉터

토큰 경계는 모델의 행동에 눈에 보이는 흔적을 남깁니다. 실무에서 반드시 알아야 할 것들입니다.

| 흉터 | 무슨 일이 일어나나 | 결과 |
|---|---|---|
| **철자 접근 불가** | `strawberry` → `st\|ra\|w\|berry` | 글자 세기·거꾸로 쓰기 실패 (§4.5) |
| **숫자 분할** | `1234` 가 `12\|34` 같은 임의 조각으로 | 산술 성능 저하. 그래서 최근 모델은 숫자를 강제로 한 자리씩 쪼갠다 |
| **공백 민감성** | `"strawberry"` 4토큰 vs `" strawberry"` 3토큰 (§4.5) | 프롬프트 끝의 공백 하나가 결과를 바꾼다 |
| **글자 경계 침범** | 우리 실험에서 ` 벡터` → `·⟨ebb2⟩\|⟨a1ed84b0⟩` | 한 토큰이 "벡의 마지막 바이트 + 터 전체"를 걸친다 |
| **미학습 토큰** | 어휘엔 있지만 학습에서 거의 안 나온 조각 | 예측 불가능한 출력 |

네 번째 줄이 특히 낯설 겁니다. **byte-level BPE 의 토큰은 글자 경계를 지킬 의무가 없습니다.** 사람에게는 기괴하지만 모델에게는 아무 문제도 아닙니다 — 모델은 애초에 "글자"라는 개념을 모르고 정수 ID 만 보기 때문입니다.

### 1.7 BPE 말고 다른 방식은

셋을 알아 두면 충분합니다.

| 방식 | 합칠 쌍을 고르는 기준 | 쓰는 곳 |
|---|---|---|
| **BPE** | **빈도** 가 가장 높은 쌍 | GPT 계열, Llama, 대부분의 LLM |
| **WordPiece** | 언어모델 **우도(likelihood) 증가량** 이 가장 큰 쌍 | BERT ([[Day-038]]) |
| **Unigram LM** | 큰 어휘에서 **가지치기** (덜어내는 방향) | T5, SentencePiece 기본값 |

WordPiece 는 $\frac{P(ab)}{P(a)P(b)}$ 를 최대화하는 쌍을 고릅니다 — 단순 빈도가 아니라 "따로 있을 때보다 붙어 있을 때 얼마나 더 그럴듯한가"입니다. Unigram 은 방향이 반대로, 후보 어휘를 크게 잡고 **손실이 가장 적게 늘어나는 조각부터 제거** 합니다. 실무 성능 차이는 크지 않고, **어느 데이터로 학습했는지가 훨씬 큰 변수** 입니다(§4.3).

## 2. 직관 / 비유 (Intuition)

> [!tip] 비유 — 활자를 짜는 조판공
> 옛날 인쇄소의 조판공은 활자 상자에서 글자를 하나씩 집어 판을 짭니다. 글자 하나씩 집으면 **어떤 문장이든 짤 수 있지만 한없이 느립니다.** 반대로 문장 전체를 통짜 활자로 만들어 두면 빠르지만, 새 문장이 나오면 아무것도 못 합니다.
>
> 노련한 조판공은 **자주 쓰는 조합만 통 활자로 미리 만들어 둡니다.** `the`, `-tion`, `검색`, `습니다`. 자주 나오니까 만들어 둘 값어치가 있고, 드문 말은 그때그때 낱 글자로 짭니다. 상자 크기(어휘)는 유한하니 무엇을 통 활자로 만들지 **골라야** 하고, 그 선택의 기준은 **인쇄소가 주로 무슨 책을 찍느냐** 입니다.
>
> 영어 소설만 찍던 인쇄소의 활자 상자를 그대로 한국어 인쇄소에 가져다 놓으면 어떻게 될까요? 한글 조합 활자가 거의 없으니 **한 글자를 짜는 데도 낱 조각을 여러 개 집어야 합니다.** 같은 분량의 원고에 시간과 품이 몇 배로 듭니다. 이게 §4.3 에서 볼 `2.76배`·`3.20배` 의 정체입니다 — 한국어가 어려운 언어라서가 아니라, **활자 상자를 남의 원고로 짰기 때문** 입니다.
>
> A typesetter who sets letter by letter can print anything but is unbearably slow; one who casts whole sentences is fast but useless on new text. The craft is casting *only the frequent combinations* as single slugs — and which combinations those are depends entirely on what the shop usually prints. Hand an English shop's type case to a Korean shop and every syllable costs several pieces. That, not linguistic difficulty, is the `2.76×` we measure below.

## 3. 한 장의 그림 (One Picture)

```text
   ── 분절 단위의 선택 ──────────────────────────────────────────────────────
     단어    [정보][검색][은]            어휘 폭발 + 미등록어(OOV)
     글자    [정][보][검][색][은]        어휘는 작지만 T 가 길어짐 -> O(T^2)
     서브워드 [정보][검색][은]            <- BPE. 빈도 높은 것에 짧은 표현

   ── BPE 학습: '자주 붙어 나오는 쌍'을 반복해서 합친다 ─────────────────────
     시작:  모든 텍스트를 바이트 1개씩으로 쪼갠다            어휘 = 256

       "다" 는 UTF-8 로   eb 8b a4   (세 바이트)

       merge #7    8b + a4      -> ⟨8ba4⟩     빈도 40
       merge #15   eb + ⟨8ba4⟩  -> "다"       빈도 31   <== 글자 하나 완성!
       merge #18   "다" + "."   -> "다."      빈도 30   <== 그 다음은 관용구

     한글 한 글자를 어휘에 넣으려면 merge 가 '두 번' 필요하다.
     영어 'a' 는 처음부터 어휘에 있다.  <- 격차는 여기서 시작된다

     규칙을 N 개 배우면   어휘 = 256 + N

   ── 같은 문장, 어휘만 다르게 (KO 39자 / EN 82자) ─────────────────────────
       어휘  300     KO 70토큰   EN 61토큰
       어휘  500     KO 46토큰   EN 39토큰
       어휘  880     KO 38토큰   EN 29토큰   <- merge 고갈(코퍼스가 작아서)

   ── 비용은 언어가 아니라 '누구 데이터로 어휘를 만들었나'가 정한다 ─────────
       학습 코퍼스        KO 글자/토큰   EN 글자/토큰   한국어 비용배수
       KO 1 : EN 1           1.03          2.83          2.76x
       KO 1 : EN 9           1.03          3.28          3.20x    <- 벌어짐
       KO 9 : EN 1           1.30          2.83          2.18x    <- 좁혀짐

   ── 그리고 유명한 실패 ────────────────────────────────────────────────────
       'strawberry'  ->  st | ra | w | berry  ->  ID [282, 264, 119, 267]
       모델이 보는 것은 글자가 아니라 위 네 개의 정수다.
       "r 이 몇 개?" 는 입력에 드러나 있지 않은 '간접 추론' 문제가 된다.
```

> One arc: words explode, characters explode the sequence, subwords compromise. BPE builds that compromise by repeatedly merging the most frequent adjacent pair — and because Hangul is three UTF-8 bytes per syllable, a single Korean character needs *two* merges before it even enters the vocabulary. Everything else (the `2.76×` cost ratio, the `strawberry` failure) follows from that starting asymmetry.

## 4. 실습 (Hands-on)

> 환경: **Windows + PowerShell**, 패키지는 **uv** 로 관리.

전체 스크립트는 이 노트 옆의 **`bpe_from_scratch.py`** 입니다. 외부 패키지가 **없고** 1초 안에 끝납니다.

```powershell

```

학습 코퍼스는 이 트랙의 주제(IR·NLP·LLM)로 쓴 **한국어 30문장 + 영어 30문장** 이고, 평가에는 **코퍼스에 없는 문장** 을 씁니다.

```python
TEST_KO = "밀집 검색은 질문과 문서를 같은 벡터 공간에 두고 가까운 것을 고른다."   # 39자, 95바이트
TEST_EN = "Dense retrieval embeds the question and the document into one shared vector space."  # 82자, 82바이트
```

핵심 학습 루프는 이게 전부입니다.

```python
# (발췌) bpe_from_scratch.py — BPE 학습
def train_bpe(corpus, vocab_size, trace=0):
    freqs = Counter(pretokenize(corpus))
    # 시작점: 모든 단어를 '바이트 하나'씩 쪼갠 상태. 기본 어휘 = 256개 바이트.
    words = {w: tuple(bytes([b]) for b in w.encode("utf-8")) for w in freqs}

    merges = []
    for step in range(vocab_size - 256):
        stats = pair_stats(words, freqs)                  # 인접 쌍의 빈도
        if not stats:
            break
        pair, count = stats.most_common(1)[0]             # 가장 흔한 쌍
        if count < 2:                                     # 한 번뿐이면 합칠 가치가 없다
            break
        merges.append(pair)                               # 순서가 곧 규칙이다
        words = {w: merge_word(s, pair) for w, s in words.items()}
    return merges, log
```

### 4.1 실험 1 — BPE 는 무엇을 '학습'하는가

merge 가 생기는 순서를 처음 24개까지 찍어 봤습니다. `⟨…⟩` 는 **아직 글자를 완성하지 못한 바이트 조각** 이고, `·` 는 공백입니다.

```text
  학습 시간 0.92s · merge 규칙 624개 · 어휘 880개

    #  합쳐진 조각        빈도       #  합쳐진 조각        빈도
    1  ·⟨eb⟩             94       13  는                32
    2  ⟨ec9d⟩            91       14  ⟨eba5⟩            31
    3  ·⟨ec⟩             81       15  다                31
    4  ⟨ed95⟩            45       16  en                31
    5  ·t                44       17  ·s                31
    6  ·⟨ea⟩             41       18  다.               30
    7  ⟨8ba4⟩            40       19  at                29
    8  ·a                38       20  이                28
    9  in                37       21  he                26
   10  on                36       22  를                25
   11  ⟨eb8a⟩            33       23  er                23
   12  re                33       24  ar                23
```

**① 1등이 `공백 + ⟨eb⟩` 라는 게 모든 것을 말해 줍니다.** `eb` 는 한글 음절의 UTF-8 **선두 바이트** 중 하나입니다. 즉 BPE 가 코퍼스에서 발견한 가장 흔한 패턴은 "**한국어 단어가 시작된다**"였습니다. 의미 있는 조각이 아니라 **문자 인코딩의 부산물** 입니다.

**② 한글 한 글자가 만들어지는 과정을 따라가 보세요.** `다` 는 UTF-8 로 `eb 8b a4` 입니다.

```text
   merge #7    8b + a4      -> ⟨8ba4⟩    (빈도 40)   아직 글자가 아니다
   merge #15   eb + ⟨8ba4⟩  -> "다"      (빈도 31)   드디어 글자 하나
   merge #18   "다" + "."   -> "다."     (빈도 30)   그 다음에야 관용구
```

같은 패턴이 `는`(#11 `⟨eb8a⟩` → #13 `는`), `이`(#2 `⟨ec9d⟩` → #20 `이`), `를`(#14 `⟨eba5⟩` → #22 `를`)에서 반복됩니다. **한국어는 어휘 예산의 상당 부분을 "글자를 만드는 데" 먼저 씁니다.** 영어는 `a`·`t`·`s` 가 처음부터 어휘에 있고, merge 예산을 **곧바로** `in`·`on`·`re`·`en`·`at`·`he`·`er`·`ar` 같은 형태소 조각에 씁니다.

> [!warning] 여기서 격차가 시작됩니다
> 이건 "한국어가 복잡한 언어"라서가 아닙니다. **UTF-8 이 ASCII 에 1바이트를, 한글에 3바이트를 준 설계 결정** 이 BPE 의 출발선을 어긋나게 만든 것입니다. 영어는 0번째 merge 부터 이미 "글자 위"에서 시작하고, 한국어는 merge 를 여러 개 써서 겨우 같은 출발선에 섭니다. 어휘 예산이 작을수록 이 손해가 커집니다 — §4.2 에서 어휘 300 일 때 한국어가 **글자 수보다 훨씬 많은 토큰**(39자 → 70토큰)을 쓰는 이유입니다.

### 4.2 실험 2 — 어휘 크기를 키우면 무슨 일이 일어나나

같은 문장을, 어휘 크기만 다르게 학습한 토크나이저로 인코딩합니다.

```text
  [어휘 300]  KO  70토큰 · EN  61토큰
    KO  ⟨eb⟩|⟨b0⟩|⟨80ec⟩|⟨a7⟩|⟨91⟩|·⟨ea⟩|⟨b2⟩|⟨80ec⟩|⟨83⟩|⟨89⟩|은|·⟨ec⟩|⟨a7⟩|⟨88⟩|…
    EN  D|en|s|e|·|re|t|r|i|e|v|al|·|e|m|b|e|d|s|·the|·|q|u|es|t|ion|·a|n|d|·the|…

  [어휘 500]  KO  46토큰 · EN  39토큰
    KO  ⟨ebb0⟩|⟨80ec⟩|⟨a7⟩|⟨91⟩|·검색|은|·⟨ec⟩|⟨a7⟩|⟨88⟩|⟨eb⟩|⟨acb8⟩|⟨eab3⟩|⟨bc⟩|·문서|를|…
    EN  D|en|s|e|·retriev|al|·e|mb|ed|s|·the|·|qu|es|t|ion|·and|·the|·document|…

  [어휘 880]  KO  38토큰 · EN  29토큰   (요청 1000 -> 실제 880: merge 고갈)
    KO  …|·검색은|·⟨ec⟩|⟨a7⟩|⟨88⟩|⟨eb⟩|⟨acb8⟩|⟨eab3⟩|⟨bc⟩|·문서를|·⟨eab0⟩|⟨99⟩|은|·⟨ebb2⟩|⟨a1ed84b0⟩|…
    EN  D|en|s|e|·retrieval|·embed|s|·the|·qu|es|t|ion|·and|·the|·document|·into|·one|…
```

**① 어휘를 키우면 조각이 길어집니다.** 영어 쪽이 특히 선명합니다.

| 어휘 | `retrieval` 의 분절 |
|---|---|
| 300 | `re\|t\|r\|i\|e\|v\|al` (7토큰) |
| 500 | `·retriev\|al` (2토큰) |
| 880 | `·retrieval` (**1토큰**) |

**② 한국어도 줄지만 방식이 다릅니다.** `·검색`(어휘 500) → `·검색은`(어휘 880) 처럼 **조사가 붙은 통 단위** 가 등장합니다. 이건 교착어에서 자연스러운 결과이면서 동시에 낭비이기도 합니다 — `검색은`·`검색을`·`검색이` 가 각각 별도 토큰을 차지하기 때문입니다.

**③ 그리고 눈여겨볼 토큰이 하나 있습니다.**

```text
   " 벡터"  ->  ·⟨ebb2⟩ | ⟨a1ed84b0⟩
                 ^^^^^^   ^^^^^^^^^^
                 벡의 앞 2바이트   벡의 마지막 바이트 + 터 전체
```

두 번째 토큰이 **글자 경계를 가로지릅니다.** 사람 눈에는 말이 안 되는 조각이지만, 모델에게는 아무 문제가 없습니다 — 모델은 "글자"를 모르고 정수 ID 만 보기 때문입니다. §1.6 에서 예고한 흉터가 실제로 찍힌 것입니다.

**④ 어휘 3000 을 요청했는데 880 에서 멈췄습니다.** 코퍼스에 "두 번 이상 인접해 나오는 쌍"이 고갈됐기 때문입니다. 그래서 어휘 1000 과 3000 의 결과가 **완전히 동일** 합니다. 실무적 함의가 큽니다: **어휘 크기는 데이터가 허락하는 만큼만 커집니다.** GPT-4 급 토크나이저의 어휘 10만은 그만한 코퍼스가 있어야 의미가 있습니다.

### 4.3 실험 3 — 한국어는 왜 토큰을 더 먹는가: 언어인가, 데이터인가

**오늘의 핵심 실험입니다.** 같은 알고리즘·같은 목표 어휘로, **학습 코퍼스의 언어 비율만** 바꿔서 세 개의 토크나이저를 만듭니다. 평가 문장은 셋 다 동일합니다.

```text
  평가 문장 (학습 코퍼스에 없음)
    KO: 밀집 검색은 질문과 문서를 같은 벡터 공간에 두고 가까운 것을 고른다.  (39자, 95바이트)
    EN: Dense retrieval embeds the question and the document into one shared vector space.  (82자, 82바이트)

  학습 코퍼스 구성          어휘   KO토큰  EN토큰  KO자/톡  EN자/톡  비용배수  KO 미완성
  ------------------------------------------------------------------------------------
  균형       (KO 1 : EN 1)   880     38     29    1.03    2.83    2.76x     74%
  영어 편중   (KO 1 : EN 9)  1328     38     25    1.03    3.28    3.20x     74%
  한국어 편중 (KO 9 : EN 1)  1460     30     29    1.30    2.83    2.18x     70%
```

읽는 법: **`비용배수`** = 같은 글자 수를 보낼 때 한국어가 영어의 몇 배 토큰을 쓰는가. **`KO 미완성`** = 한 글자를 완성하지 못한 조각(`⟨16진수⟩`)의 비율.

**① 균형 코퍼스에서도 이미 `2.76배` 입니다.** 데이터를 반반으로 줘도 한국어가 손해입니다 — §4.1 에서 본 **3바이트 출발선** 때문입니다.

**② 영어를 9배로 늘리면 `3.20배` 로 벌어집니다.** 흥미로운 건 **한국어 쪽이 나빠진 게 아니라 영어 쪽이 좋아졌다** 는 점입니다(KO 는 `1.03` 그대로, EN 이 `2.83 → 3.28`). 어휘 예산이 늘어난 만큼 전부 영어 조각에 쓰인 것입니다. **다른 언어 사용자는 자기 언어가 나빠져서가 아니라, 개선이 자기에게 오지 않아서 뒤처집니다.**

**③ 한국어를 9배로 늘리면 `2.18배` 로 좁혀집니다.** KO 가 `1.03 → 1.30` 으로 개선되고 토큰 수가 `38 → 30` 으로 줄었습니다. **즉 이 격차는 언어의 운명이 아니라 데이터 배분의 결과입니다.**

**④ 그런데 `KO 미완성` 은 `74% → 70%` 로 거의 안 움직입니다.** 우리 코퍼스가 작아 한국어 음절을 다 담지 못하기 때문입니다(한글 음절은 이론상 11,172자). 실제 상용 토크나이저는 어휘가 10만 이상이라 흔한 음절은 대부분 통 토큰으로 갖고 있어, 이 비율이 훨씬 낮습니다.

> [!warning] 우리 실험은 '과장된 축소판'입니다
> 위 `2.76x`·`3.20x` 를 실제 API 비용 배수로 그대로 쓰면 안 됩니다. 우리 코퍼스는 60문장, 어휘는 1000 안팎입니다. 상용 토크나이저(GPT-4 계열의 `cl100k_base`·`o200k_base`, Llama 3 등)는 어휘가 10만~20만이고 한국어 데이터도 훨씬 많이 봐서 **격차가 이보다 작습니다.** 이 실험이 보여 주는 것은 **정확한 크기가 아니라 방향과 원인** 입니다 — ① 격차는 실재하고, ② 원인은 UTF-8 바이트 수와 코퍼스 배분이며, ③ **데이터 비율을 바꾸면 격차도 바뀝니다.** 여러분 서비스의 실제 배수가 궁금하다면 쓰는 모델의 토크나이저로 직접 재야 합니다(§4.6 의 (5)).

실무적으로 이 표는 세 가지를 뜻합니다.

- **비용**: 대부분의 API 는 토큰 단위로 과금합니다. 같은 내용이라도 한국어 프롬프트가 더 비쌉니다.
- **문맥 창**: "128K 토큰"은 언어마다 실제 담기는 **분량이 다릅니다.** RAG 에서 몇 개의 청크를 넣을 수 있는지가 달라집니다(Phase 6).
- **성능**: 토큰이 잘게 쪼개질수록 시퀀스가 길어지고, 같은 의미를 표현하는 데 더 많은 스텝이 필요합니다.

### 4.4 실험 4 — 학습에 없던 문자: OOV 가 없다는 뜻

byte-level 의 약속을 확인합니다. 학습 코퍼스에 이모지도, 그리스 문자도, 희귀 한자도 없었습니다.

```text
  딥러닝    ->  8토큰  ⟨eb⟩|⟨94⟩|⟨a5⟩|⟨eb⟩|⟨9f⟩|⟨ac⟩|⟨eb8b⟩|⟨9d⟩
  🍓 딸기   ->  7토큰  ⟨f0⟩|⟨9f⟩|⟨8d⟩|⟨93⟩|·⟨eb94⟩|⟨b8⟩|기
  Ωμέγα     -> 10토큰  ⟨ce⟩|⟨a9⟩|⟨ce⟩|⟨bc⟩|⟨ce⟩|⟨ad⟩|⟨ce⟩|⟨b3⟩|⟨ce⟩|⟨b1⟩
  龘        ->  3토큰  ⟨e9⟩|⟨be⟩|⟨98⟩
```

**전부 인코딩됐습니다. `<UNK>` 는 한 번도 나오지 않았습니다.** 이게 byte-level 의 약속입니다.

동시에 **대가도 그대로 보입니다.** `Ωμέγα` 는 5글자인데 **10토큰** 입니다 — merge 를 하나도 배우지 못해 바이트 낱개로 흩어졌습니다. `딥러닝` 도 3글자에 8토큰입니다("딥"·"러"는 코퍼스에 없었고, `⟨eb8b⟩` 만 다른 글자에서 배운 조각을 재활용).

> [!tip] OOV 는 사라진 게 아니라 '비용'으로 바뀌었습니다
> 단어 단위 토크나이저에서 미등록어는 **정보 손실**(`<UNK>` 로 뭉개짐)이었습니다. byte-level BPE 에서는 정보가 보존되는 대신 **토큰을 많이 먹습니다.** 손실이 비용으로 환전된 셈이고, 이게 훨씬 나은 거래입니다 — 비용은 어휘를 키우거나 데이터를 늘려 줄일 수 있지만, 잃어버린 정보는 되찾을 수 없기 때문입니다.

### 4.5 실험 5 — `strawberry` 의 `r` 은 몇 개인가

가장 유명한 LLM 실패담입니다. 왜 그런지를 **토큰 경계로** 설명합니다. berry 계열 단어를 자주 본 코퍼스로 어휘 1200 짜리 토크나이저를 학습시켰습니다.

```text
  모델이 실제로 보는 것:
    'strawberry'    -> 4토큰  st|ra|w|berry     ID [282, 264, 119, 267]
    ' strawberry'   -> 3토큰  ·stra|w|berry     ID [985, 119, 267]
    'raspberry'     -> 4토큰  ra|s|p|berry      ID [264, 115, 112, 267]
    'blueberry'     -> 5토큰  b|l|u|e|berry     ID [98, 108, 117, 101, 267]
```

`strawberry` 안의 `r` 은 **3개** 입니다. 그런데 토큰 경계는 `st|ra|w|berry` 이고, 모델의 실제 입력은 `[282, 264, 119, 267]` **네 개의 정수** 입니다.

`267` 이라는 정수 안에 "`berry` 에는 `r` 이 두 개 있다"는 사실은 **명시되어 있지 않습니다.** 모델이 그걸 알려면 학습 중에 임베딩 벡터 안에 철자 정보를 **간접적으로** 심어 두었어야 합니다. 사람으로 치면 **글자를 보고 세는 게 아니라, 단어의 생김새를 기억으로 떠올려 세는 것** 에 가깝습니다.

**공백 하나가 분절을 바꾸는 것도 여기서 보입니다.** `'strawberry'` 는 `st|ra|w|berry`(4토큰)인데 `' strawberry'` 는 `·stra|w|berry`(3토큰)입니다. 같은 단어인데 **앞의 공백 유무로 첫 토큰이 달라집니다.** 프롬프트 끝에 공백을 남기면 모델이 다른 것을 보게 되는 이유입니다.

**결정적인 증거는 이겁니다.** 토큰 경계를 강제로 글자에 맞추면 같은 질문이 쉬워집니다.

```text
  's t r a w b e r r y'
   -> 11토큰  s|·t|·r|·a|·w|·b|·e|·r|·r|·|y
```

이제 `r` 이 **입력 시퀀스에 세 번 명시적으로 등장** 합니다. 세는 일은 [[Day-040]] 에서 확인한 attention 의 특기입니다 — 각 위치를 직접 보면 되니까요.

> [!warning] 이 실패에서 무엇을 배울 것인가
> **"모델이 멍청하다"가 아니라 "질문이 모델의 입력 표현에 드러나지 않는다"** 입니다. 같은 모델·같은 가중치인데 **토큰화만 바꿔서 난이도가 달라집니다.** 그래서 이 종류의 문제(글자 세기, 거꾸로 쓰기, 각운, 애너그램, 정확한 자릿수 산술)는 규모를 키워도 잘 안 낫고, **표현을 바꾸거나(글자 분리) 도구를 주면(코드 실행) 즉시 낫습니다.** [[Day-040]] §4.4 에서 본 "무엇을 아는가 vs 어떻게 말하는가"의 구분에, 오늘 **"무엇을 볼 수 있는가"** 라는 세 번째 축이 추가된 셈입니다.

## 5. 용어집 (Glossary)

| 용어 | English | 한 줄 뜻 |
|------|---------|---------|
| 토큰화 | tokenization | 텍스트를 모델이 다루는 최소 단위(정수 ID)로 바꾸는 과정 |
| 서브워드 | subword | 단어보다 작고 글자보다 큰 분절 단위. 어휘 폭발과 시퀀스 폭발 사이의 타협 |
| 바이트 쌍 부호화 | byte-pair encoding (BPE) | 가장 자주 인접하는 쌍을 반복해서 합쳐 어휘를 만드는 알고리즘 |
| merge 규칙 | merge rule | "이 두 조각을 합쳐라"는 지시. **순서** 가 곧 토크나이저의 정체 |
| 바이트 수준 BPE | byte-level BPE | 최소 단위를 바이트(256개)로 잡는 변형. OOV 가 원리적으로 없다 |
| 미등록어 | out-of-vocabulary (OOV) | 어휘에 없는 입력. 단어 단위에서는 정보 손실, byte-level 에서는 토큰 비용 |
| 사전 분할 | pre-tokenization | BPE 이전에 공백·구두점으로 미리 나누는 단계. merge 가 단어를 넘지 못하게 막는다 |
| 압축률 | compression ratio | 글자 수 ÷ 토큰 수. 높을수록 같은 내용을 적은 토큰으로 표현 |
| 미학습 토큰 | glitch token | 어휘엔 있지만 학습에서 거의 안 나온 토큰. 예측 불가능한 출력의 원인 |
| WordPiece | WordPiece | 빈도 대신 우도 증가량으로 쌍을 고르는 변형. BERT 가 사용 |
| Unigram LM | unigram language model | 큰 후보 어휘에서 손실이 적게 늘어나는 조각부터 제거하는 방식. SentencePiece 기본값 |

## 6. 생각거리 (Reflection)

> [!question] 스스로 답해 보기
> 1. **토크나이저는 왜 모델보다 먼저 정해지는가.** BPE 학습은 모델 학습 전에 딱 한 번 일어나고, 그 뒤로는 바꿀 수 없습니다(어휘를 바꾸면 임베딩 행렬이 통째로 무의미해집니다). 그렇다면 새 언어·새 도메인을 잘 지원하려면 **언제** 개입해야 할까요? 이미 배포된 모델의 한국어 효율을 개선하려면 어떤 선택지가 있을까요?
> 2. **`2.76x` 를 어떻게 줄일 것인가.** §4.3 은 데이터 비율을 바꾸면 배수가 움직인다는 걸 보여 줬습니다. 그런데 다국어 모델은 100개 언어를 지원해야 합니다. 한정된 어휘 예산을 언어들에 어떻게 나눠야 "공정"할까요? 사용자 수 비례? 균등? 화자 수 비례? 각 기준이 누구에게 유리한가요?
> 3. **`⟨a1ed84b0⟩` 같은 토큰이 존재해도 괜찮은가.** 글자 경계를 가로지르는 조각을 모델은 문제없이 씁니다. 그렇다면 "토큰이 언어학적으로 의미 있는 단위여야 한다"는 직관은 틀린 걸까요? 반대로 이런 조각이 **해로울 수 있는** 상황을 하나 상상해 보세요.
> 4. **글자 단위로 돌아가면 안 되나.** OOV 도 없고, `strawberry` 문제도 없고, 어휘도 작습니다. 그런데 아무도 안 씁니다. [[Day-040]] 의 $O(T^2)$ 와 §1.1 의 표를 근거로, 시퀀스가 4배 길어질 때 실제로 무엇이 얼마나 비싸지는지 계산해 보세요. 그 비용을 감당할 수 있게 하는 기술이 있다면 무엇일까요?
> 5. **[[Day-006]] 을 다시 읽어 보세요.** 그때 배운 규칙 기반 토큰화(공백 분리·정규화·불용어 제거)를 오늘의 BPE 와 나란히 놓아 보세요. BPE 가 대체한 것은 무엇이고, **여전히 사람이 정해야 하는 것** 은 무엇인가요? (힌트: `pretokenize` 의 정규식은 누가 썼나요?)

## 7. 오늘의 한 줄 요약 (Takeaway)

> [!summary]
> **토크나이저는 전처리가 아니라 모델이 세상을 보는 해상도이며, 그 해상도조차 학습된다.** BPE 는 다섯 줄짜리 알고리즘이다 — 가장 자주 인접하는 쌍을 반복해서 합치고, **합친 순서** 를 규칙으로 저장한다(어휘 = 256 + merge 수). from scratch 로 학습시켜 보니 1등 규칙이 `공백+⟨eb⟩`(빈도 94)였고, **한글 "다" 는 merge 두 번**(`8b+a4` → `eb+⟨8ba4⟩`)을 써야 어휘에 들어온 반면 영어 `a`·`t` 는 처음부터 있었다 — 여기서 모든 격차가 시작된다. 어휘를 300→880 으로 키우자 같은 문장이 **KO 70→38, EN 61→29 토큰** 으로 줄었지만(`retrieval` 이 7→1토큰), 코퍼스가 작아 **880 에서 merge 가 고갈** 됐다: 큰 어휘는 큰 데이터를 전제한다. 핵심 실험은 §4.3 이다 — 같은 알고리즘으로 코퍼스 비율만 바꾸니 한국어 비용배수가 **균형 `2.76x` → 영어편중 `3.20x` → 한국어편중 `2.18x`** 로 움직였다. 그것도 한국어가 나빠져서가 아니라 **개선이 영어에만 갔기 때문** 이다(KO `1.03` 고정, EN `2.83→3.28`). 즉 **한국어가 비싼 게 아니라 어휘를 남의 데이터로 만든 것** 이다. byte-level 덕분에 이모지·희귀 한자까지 `<UNK>` 없이 인코딩되지만 대가는 토큰 수다(`Ωμέγα` 5글자 = 10토큰) — **OOV 가 정보 손실에서 비용으로 환전** 됐다. 마지막으로 `strawberry` → `st|ra|w|berry` → `[282, 264, 119, 267]`: `r` 이 3개라는 사실은 입력에 **드러나 있지 않고**, 글자마다 띄어 쓰면 같은 질문이 쉬워진다. [[Day-040]] 의 "무엇을 아는가 vs 어떻게 말하는가"에 오늘 **"무엇을 볼 수 있는가"** 가 더해졌다. 다음 편([[Day-042]])에서는 [[Day-040]] §4.4 가 예고한 **디코딩 전략** 으로 들어간다.
